## 1. 목적

요구사항 추적 매트릭스(RTM)는 소프트웨어 개발 전 과정에서 각 요구사항이 설계, 구현, 테스트 단계에 올바르게 반영되었는지를 추적하기 위한 문서이다.

본 문서의 목적은 다음과 같다:

- **완전성 보장**: 모든 요구사항이 설계, 구현, 테스트에 빠짐없이 반영되었는지 확인한다.
- **일관성 유지**: 요구사항 변경 시 영향 받는 설계, 코드, 테스트를 신속히 파악한다.
- **진행률 관리**: 요구사항별 구현 및 테스트 진행 상태를 한눈에 파악한다.
- **품질 확인**: 테스트 커버리지를 통해 품질 수준을 정량적으로 측정한다.
- **변경 영향 분석**: 요구사항 변경 시 영향 범위를 파악하여 리스크를 관리한다.

## 2. 추적 범위

[서비스 기획서](../00-기획/서비스기획서.md)(SPD-CHUP-v0.2)의 포함 범위(MVP-001~020)와 [비즈니스 정책서](../00-기획/비즈니스정책서.md)(BPD-CHUP-v0.2)의 개별 규칙을 [SRS](요구사항명세서-SRS.md)의 FR·NFR에 연결한다. UC는 [유스케이스 명세서](유스케이스명세서.md)(UCS-CHUP-v0.1)를 따른다.

- 추적 대상: FR-001~023 (P1~P3), NFR-001~014.
- 제외 요구사항 FR-024(유료 결제·매출 배분), FR-025(외부 알림)은 상태 "보류"로 행만 남기고 설계·구현·테스트를 연결하지 않는다.
- MVP-ID와 FR의 대응: 모든 MVP-001~020이 하나 이상의 FR에 연결되어 있다 (6장 역방향 표).

## 3. 상태 정의

### 3.1 요구사항 상태

| 상태 | 설명 |
|------|------|
| 초안 (Draft) | 최초 작성 상태, 검토 필요 |
| 승인 (Approved) | 이해관계자 검토 및 승인 완료 |
| 변경중 (Changing) | 승인 후 변경 요청 발생 |
| 보류 (On Hold) | 일시적으로 구현 보류 |
| 삭제 (Deleted) | 요구사항에서 제외됨 |

### 3.2 매핑 상태

| 상태 | 설명 |
|------|------|
| 미착수 (Not Started) | 해당 단계 작업이 시작되지 않음 |
| 진행중 (In Progress) | 해당 단계 작업이 진행 중 |
| 완료 (Completed) | 해당 단계 작업이 완료됨 |
| N/A | 해당 단계가 적용되지 않음 |

## 6. 커버리지 요약

기준선의 현재 릴리스(v1.0 MVP)에서 해당 단계가 적용되는 요구사항을 분모로 삼는다. FR-024·025(보류)와 사업자 관리 항목 NFR-007은 분모에서 뺀다.

| 지표 | 계산 | 실적 |
| --- | --- | --- |
| 설계 매핑률 | 설계 참조가 있는 요구사항 / 설계 대상 요구사항 | 35 / 36 (97%) — NFR-008 미결 |
| 구현 매핑률 | 구현 참조가 있는 요구사항 / 구현 대상 요구사항 | 20 / 36 (56%) — FR 13개(001·002·004·010~015·017~020, FR-020은 계산 함수만), NFR 7개(001·004·010~014). 이 중 "일부 구현"이 다수 |
| 테스트 매핑률 | TC가 연결된 요구사항 / 검증 대상 요구사항 | 35 / 35 (100%) — TC 정의 기준 (NFR-013은 CI 점검) |
| TC 실행 요구사항 비율 | 실행된 TC가 하나 이상인 요구사항 / 검증 대상 | 21 / 35 (60%) |
| 수용 기준 검증 완료율 | 연결된 TC가 모두 통과한 요구사항 / 검증 대상 요구사항 | 2 / 35 (6%) — FR-010, FR-014 |

분모: FR-001~023 (23개) + NFR-001~006, 008~014 (13개) = 36개. 테스트 분모는 NFR-013을 뺀 35개.

테스트 매핑은 검증 준비 상태이다. 실행률과 통과율은 후보 빌드의 실제 TC 판정을 바탕으로 테스트 결과 보고서에서 확인한다.

### 7.2 미매핑 항목 관리 규칙

1. 미결 항목마다 사유, 담당자, 해결 기한을 기록한다.
2. 단계 검토에서 남은 미결 항목이 다음 단계에 미치는 영향을 확인한다.
3. 승인된 요구사항이 바뀌면 변경 요청을 연결하고 관련 설계·구현·테스트를 함께 갱신한다.

### 7.3 단계별 확인 기준

| 단계 전환 | RTM 확인 항목 |
| --- | --- |
| G1 요구사항 → 시스템 설계 | 승인 범위의 요구사항 행에 출처와 SRS 수용 기준이 있다. (현재: 모든 FR 행에 출처·수용 기준 있음, 승인 전) |
| G2 시스템 설계 → 상세 설계 | 시스템 수준에서 적용되는 설계 결정·자료를 연결한다. (현재: 02 문서 미작성 — 미충족) |
| G3 상세 설계 → 구현 | 구현 대상에 상세 설계 또는 대응 작업 참조를 연결한다. (현재: DDS 절 연결 완료, NFR-008 제외) |
| G4 구현 → 테스트 | 테스트 대상 요구사항에 구현 참조와 수용 기준에 맞춘 TC를 연결하고 후보 빌드를 기록한다. |
| G5 테스트 → 배포 | 대상 빌드의 테스트 판정과 증빙, 허용된 제외 결정과 승인 기록을 연결한다. |

단계별 승인과 예외 처리 기준은 [검토 체크리스트](../08-검토/단계별검토-체크리스트.md)에서 확인한다.

## 8. RTM 갱신 절차

| 이벤트 | 갱신 항목 | 담당자 |
|--------|----------|--------|

| 유스케이스 작성/변경 | UC 매핑 열 갱신 | BA |
| 설계 문서 작성/변경 | 설계 문서 참조 열 갱신 | 설계자 |

| 테스트 실행 완료 | 테스트 상태 갱신 | QA |
| 정기 점검 (주간) | 전체 커버리지 요약 갱신 | PM |

### 8.2 변경 영향 분석 체크리스트

요구사항 변경 시 다음 항목을 점검한다:

- [ ] 변경된 요구사항의 RTM 상태 업데이트
- [ ] 관련 유스케이스 영향 확인 및 갱신 여부 판단
- [ ] 관련 설계 문서 영향 확인 및 갱신 여부 판단
- [ ] 관련 구현 모듈 영향 확인 및 수정 범위 산정
- [ ] 관련 테스트케이스 영향 확인 및 추가/수정 여부 판단
- [ ] 연관 요구사항(의존성)에 대한 파급 효과 확인
- [ ] 커버리지 요약 재계산
