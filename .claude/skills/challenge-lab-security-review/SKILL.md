# Challenge Lab Security Review

실제로 악용할 수 있는 문제와 일반적인 우려를 구분하는 점검이에요. 원본은 `security-research`(Oh My OpenAgent 팀 모드)이고, 챌린지업에 맞게 줄였어요.

## 전제 확인

1. 메인 세션에서 실행해요(서브에이전트 안에서 다시 부르지 않음).
2. 범위는 $ARGUMENTS 로 받아요. 비어 있으면 운영 서비스 전체와 현재 브랜치의 변경분을 봐요.
3. 운영 점검은 **QA 계정만** 써요(`qa-sub-*@demo.test`, `instructor-*@demo.test`). 비밀번호는 `E2E_PASSWORD` 등 환경 변수로 받고, 출력이나 파일에 쓰지 않아요.
4. 금지: 데이터 삭제·대량 요청·부하·다른 사람 계정 사용·그로블이나 Supabase 같은 제3자 서비스 공격. 쓰기 PoC는 QA 계정의 자기 데이터에만 하고, 끝나면 되돌려요.

## 챌린지업 공격 면 (먼저 읽을 곳)

| 면 | 위치 | 확인할 것 |
|---|---|---|
| 역할·권한 | `web/src/server/actions.ts`, `store.ts` (`isMemberOf`, `isInstructorOf`, 작성자 확인) | 비회원·비참여 학생·다른 강사가 남의 챌린지·글·인증을 읽기/쓰기/수정 |
| 비공개 인증 | `submitProof` visibility, 피드·Day·커리큘럼·리더보드 화면 | 비공개 본문이 다른 사람의 HTML·RSC 응답에 실리는지 |
| 첨부 | 링크 인증 `linkUrl`, Supabase Storage | 첨부 저장소가 있다면 공개 버킷·URL 추측으로 접근되는지, 링크 값 검증(`http(s)`만) |
| 데이터 격리 | `supabase/migrations` RLS, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 공개 anon 키로 REST(`/rest/v1/<table>`) 직접 조회 시 행이 나오는지 |
| 웹훅 | `web/src/app/api/webhooks/groble/route.ts`, `server/groble.ts` | 서명·시각·중복·금액 검증 우회 |
| 클라이언트 입력 | 서버 액션 인자(글 id, Day 번호, 챌린지 id) | 남의 id를 넣었을 때 거절되는지 (혼동된 대리인) |
| 비밀값 | `web/.env.example`, 클라이언트 번들 | 서비스 키·웹훅 시크릿이 번들·저장소에 노출되는지 |

## 심각도 기준

- CWE(약점 분류)와 심각도는 따로 적어요. 참고: CWE, OWASP WSTG, OWASP ASVS, CVSS v4.0.
- 공격 경로가 없으면 심각도도 없어요. 높음 이상은 구체적인 전제 조건과 피해를 적어야 해요.
- 등급: S0 출시 차단 · S1 높음 · S2 보통 · S3 낮음 (테스트결과보고서 체계와 같음).
- 이론 설명보다 작고 재현되는 PoC를 우선해요. 안전하게 실행할 수 없으면 정적 증명으로 대신하고 한계를 적어요.

## 역할 (서브에이전트)

| 이름 | 종류 | 맡는 일 |
|---|---|---|
| surface-hunter | 읽기 전용 | 진입점·신뢰 경계·공격자가 넣을 수 있는 입력·데이터가 나가는 곳 지도 |
| authz-data-hunter | 읽기 전용 | 역할 권한, 비공개 인증 노출, 데이터 격리, 남의 id 대입, 비밀값 |
| runtime-supply-hunter | 읽기 전용 | 웹훅, 환경 변수, 훅·스크립트, 의존성, 첨부·링크 처리 |
| poc-engineer-a | 실행 | 유력 후보를 운영·로컬에서 안전한 최소 PoC로 재현 |
| poc-engineer-b | 실행 | 같은 후보를 독립적으로 재현하거나 반증, 재현 안 되면 등급 낮춤 |

여러 역할을 동시에 띄울 수 없는 환경이면 같은 순서로 차례로 실행하고 "병렬 미확인"으로 기록해요.

## 절차

1. **범위·기준선**: 기준 SHA, 운영 URL, 점검할 케이스 목록(아래 형식)을 먼저 만들어요. 케이스마다 역할·대상·입력·기대 결과를 정해요.
2. **헌터 3명 병렬**: 후보마다 제목, 위치(`파일:함수`), 공격자 능력, 공격 경로, 피해, CWE 후보, 근거, 안전한 확인 방법을 받아요. 일반적인 강화 권고는 버려요.
3. **PoC 2명**: 후보를 중복 제거하고 두 명에게 같은 후보를 보내요. 결과는 재현 / 반증 / 실행 위험 중 하나와 정확한 명령·관찰 값이에요.
4. **교차 확인**: 살아남은 것, 등급을 낮출 것, 가장 작은 수정, 재발 방지 테스트를 정해요.
5. **기록**: 아래 표를 `waterfall/05-테스트/테스트결과보고서.md`의 보안 점검 절에 추가해요. 실행하지 못한 케이스는 **미실행**과 이유를 적어요.

## 케이스 기록 형식

| 케이스 ID | 역할 | 대상 | 입력 | 기대 | 실제 | 판정 | 근거 |
|---|---|---|---|---|---|---|---|
| SEC-AUTHZ-01 | 비참여 학생 | 남의 챌린지 Day 인증 | `submitProofAction` 직접 호출 | 거절 | … | 통과 / 실패 / 미실행 / 해당 없음 | 명령·`파일:줄`·응답 |

## 최종 보고

```markdown
## 보안 점검 결과
### 판정: PASS | PASS WITH FINDINGS | BLOCK
### 범위: 대상, 기준 SHA, 운영 URL, 실행한 명령
### 발견 사항
| 등급 | 제목 | CWE | 악용 가능성 | 피해 | PoC | 수정 |
### 상세: 근거 · 공격 경로 · PoC · 등급 이유 · 최소 수정 · 재발 방지 검사
### 낮추거나 버린 후보
### 남은 위험: 확인하지 못한 것과 이유
```

- 판정을 맨 앞에 써요. 출시를 막는 문제는 숨기지 않아요.
- 추측을 취약점으로 보고하지 않아요. PoC를 통과한 발견이 없으면 그렇다고 쓰고 남은 위험을 적어요.
- 실제로 지표를 매기지 않았다면 CVSS 점수를 쓰지 않아요.
